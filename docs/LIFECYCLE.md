# 从立项到规模化：按实现阶段梳理真实问题与解法

本文按**项目真实推进顺序**组织：立项 → 数据接入 → Agent 设计 → 检索 → 输出可信 → 服务化 →
公网流量 → 重复请求 → 召回失败 → 运营迭代。每一阶段都给出：

- **会遇到什么**（症状，尽量写成用户/运维能感知的现象）
- **为什么**（根因）
- **怎么解**（本仓库已实现 / 上生产还要补）
- **怎么验证**（指标或测试）

图例：✅ 已实现且有测试 · 🟡 单机/简化版，规模化需替换 · ⛔ 明确不做（附原因）

---

## 阶段 0｜立项：先把边界钉死

| 问题 | 症状 | 解法 | 状态 |
|---|---|---|---|
| 范围失控 | "顺便让它提 PR / 跑测试 / 改代码" | 只读边界写进工具白名单与产品文案；写操作在策略层拒绝 | ✅ |
| 无法验收 | 做完不知道算不算"好" | 先定义 4 个可测指标：Recall@5、引用有效率、P95 延迟、单次成本 | ✅ |
| 责任不清 | 用户把假设当结论去改生产 | 报告标题、置信度分级、免责声明、"未执行"措辞 | ✅ |
| 数据合规 | 把私有仓库内容发给第三方模型 | 只读公开 API；`LLM_BASE_URL` 可指向私有化端点；文档写明数据出境 | ✅/🟡 |

> 立项阶段最常见的失败不是技术，而是**没定义"什么算成功"**。本项目的做法是：
> 先把评测指标和免责边界写进 README，再写代码。

## 阶段 1｜数据接入：GitHub 不是"一个 GET 就完事"

| 问题 | 症状 | 解法 | 状态 |
|---|---|---|---|
| 匿名限流 | 试几次就 403，报 "Resource not accessible" | PAT + `x-ratelimit-*` 解析 + 明确提示 | ✅ |
| 搜索独立限额 | 读 Issue 正常，搜索 403/429 | 搜索缓存 20 分钟 + 查询去重 + 轮次上限 | ✅ |
| 评论几千条 | 上下文爆炸 / 关键信息被淹没 | 分页上限 3 页 + 首尾抽样 + 显式提示"中间被跳过" | ✅ |
| 编号其实是 PR | 后续分析全错位 | 检测 `pull_request` 字段并报错 | ✅ |
| Issue 被删/私有/改名 | 404 与网络错误混为一谈 | 错误分层（404/401/403/429/5xx/网络）+ 稳定 `code` | ✅ |
| README 缺失/非标准 | 少一类证据就崩 | 失败降级为 warning，不阻塞主流程 | ✅ |
| 内容不可信 | 评论里藏注入指令 | 净化 + 打分 + nonce 隔离 + 只读工具 | ✅ |
| 突发流量打满额度 | 多人同时分析同一仓库 | ETag 304 + TTL 缓存 + 结果缓存（见阶段 7） | ✅ |

**验证**：`test_github_cache_and_read_only_request`、`test_404_ratelimit_errors`；
线上看 `github_ratelimit_remaining`、`github_cache_hits_total`。

## 阶段 2｜Agent 设计：让模型"能做主"但"停得下来"

| 问题 | 症状 | 解法 | 状态 |
|---|---|---|---|
| 单轮 RAG 召回差 | 结论空泛、答非所问 | 7 节点状态机：规划 → 工具 → 评估 → 再检索 | ✅ |
| 死循环 | 同一关键词搜 3 次，token 暴涨 | 同参去重 + 检索词去重 + 六维预算 + 轮次用尽即收尾 | ✅ |
| 工具误用 | 猜文件路径、反复读 README | 工具失败变观测；去重标记 duplicate；步数上限 | ✅ |
| 跨仓库越权 | 注入让 `repo=别的仓库` | 节点强制覆写 `repo`；查询词禁限定词 | ✅ |
| 预算耗尽就崩 | 用户等了 40s 拿到 500 | 超限 → `partial` → 确定性降级报告 | ✅ |
| 检查点白写 | 重跑重复抓取、重复烧钱 | 每节点（含失败节点）写检查点；`/resume` 从阶段续跑 | ✅ |
| 无法自纠 | 报告里全是无依据结论 | `verify` 校验 → 带批评重写一次 → 仍不过则保守输出 | ✅ |

**验证**：`test_budget_exceeded_returns_partial`、`test_resume_after_budget_failure_completes`、
`test_unsupported_claim_triggers_one_rewrite`。

## 阶段 3｜检索：召回失败才是常态

### 3.1 失败分类（先别急着换向量库）

| 类型 | 典型现象 | 判断方法 |
|---|---|---|
| A. 查询词不匹配 | 人搜得到，Agent 搜不到 | 看 `queries` 与人工检索词的差异 |
| B. 语料确实没有 | 仓库里没有同类 Issue | 空结果 + 关键词人工搜也无 |
| C. 抓取缺失 | README/评论没取到 | `warnings` 里有读取失败 |
| D. 切块丢失 | 关键行被切断 | 对比原文与命中 chunk |
| E. 排序错误 | 相关项在第 8 名 | 看 `retrieval.ranked` |
| F. 上下文截断 | 召回了但没进 Prompt | 对比 `citable_ids` 与全部证据 |
| G. 引用映射错 | 引用了不存在的 ID | 引用有效率为负 |

### 3.2 兜底链（本项目已实现的部分）

```
GitHub 关键词搜索
   └─ 为空 → 错误码/异常名回退检索（不花 LLM 调用）      ✅ build_fallback_query
        └─ 仍为空 → 记录 retrieval_empty_total，标记"该仓库可能确无同类问题"
assess 判定不足
   └─ 生成新检索词（必须是没试过的）→ 再检索（≤ MAX_ROUNDS）  ✅
本地混合检索（BM25 + 向量 + RRF + 去重）
   └─ 空 → 返回"知识库无匹配"，模型改用 get_document        ✅
证据不足
   └─ 写 gaps / 输出降级报告，不编造                          ✅
```

### 3.3 生产还应补的（按性价比排序）

1. **查询改写**：让模型生成 2~3 个同义/英文变体，多查询并行召回再 RRF 融合（成本 +1 次 LLM，召回通常 +10~20%）。
2. **标题/错误码加权**：Issue 标题与错误码的匹配权重高于正文（BM25 已做标题加权，可继续加大）。
3. **真 Embedding**：替换 `HashingEmbedder`，解决"超时 ↔ timeout"这类同义改写；
   代价是每次检索一次网络调用，需缓存向量。
4. **Cross-encoder 重排**：对 top 20 用小型 rerank 模型精排，Recall@5 通常还能再涨。
5. **评论单独建索引**：workaround 常在评论而非正文，当前评论作为一个文档整体切块。
6. **召回失败样本回流**：把 `retrieval_empty_total` 对应的查询词 + 人工搜索词加入评测集。
7. **热门仓库预建索引**：Top N 仓库离线建 chunk + 向量，线上只做检索。

**验证**：离线 Recall@5/MRR；线上 `retrieval_fallback_total`、`retrieval_empty_total`、
"用户点踩且报告说证据不足"的比例。

## 阶段 6｜公网流量：访问人数太多导致"变慢"

### 6.1 先定位瓶颈，别一上来就扩容

用一次真实运行的数据建立直觉：**53s / 29k token / 8 次工具 / 14 次 LLM 调用**。
也就是说瓶颈几乎一定在 **LLM 串行等待**，而不是 Python 或 SQLite。

按单次 53s 估算（每个并发槽位）：

```
单槽吞吐 ≈ 3600 / 53 ≈ 68 次/小时 ≈ 1,630 次/天
2 个 worker ≈ 136 次/小时 ≈ 3,260 次/天
10,000 次/天 → 需要 ≈ 7 个并发槽位（留 30% 余量）
```

对应到本项目：

| 资源 | 现状 | 放大方式 |
|---|---|---|
| LLM 并发 | 每个作业独立调用，无线程池上限 | 加全局 `Semaphore(max_concurrent_llm)`，按租户再分配 |
| 作业并发 | `JOB_WORKERS=2` | 提高 + 多副本；队列改 Redis |
| GitHub 请求 | ~8~10 次/次分析 | 结果缓存 + ETag + 多 Token / GitHub App（15k/h） |
| SQLite | WAL，单机 | 结果/记忆迁 PostgreSQL |
| SSE 连接 | 单机内存缓冲 | Redis Stream + sticky 或广播 |

### 6.2 按"成本从低到高"的优化顺序

1. **结果缓存**（阶段 7）：命中即 0 成本、0 延迟，通常能砍掉 30%~60% 的重复流量。
2. **静态资源与页面**：`index.html` 走 CDN/浏览器缓存，减少服务端渲染压力（当前是内联单文件，天然轻）。
3. **请求合并**：并发相同请求共享一次执行（已实现 single-flight）。
4. **限流与背压**：租户级 429 + `Retry-After`；队列深度超阈值直接拒绝而不是排到超时。
5. **SSE 连接上限**：每租户/每 IP 限制并发流；超限降级为轮询作业状态。
6. **模型层**：并发信号量 + 超时 + 重试预算；高峰期降级到更快的小模型或关闭 critic 节点。
7. **水平扩容**：无状态 API 多副本 + 共享 Redis/Postgres；SSE 事件放 Redis。
8. **预热**：热门仓库/高频 Issue 定时预计算，命中缓存直接返回。

### 6.3 必须同时做的"止损"设计

| 场景 | 处理 |
|---|---|
| LLM 供应商 429/5xx | 指数退避 + 抖动，重试上限 2；失败降级报告 |
| GitHub 限流 | 直接返回可执行提示，不做无意义重试 |
| 队列排队过久 | 拒绝新任务（503 + Retry-After），保护已完成任务 |
| 单次运行失控 | 六维预算 + 墙钟，超限立即降级 |
| 成本异常 | 按租户预算 + 全局日预算；命中阈值告警 |

### 6.4 容量与成本表（按实测 29k token / 53s）

| 日分析量 | 需并发槽位 | Token/日 | 成本/日（按 $0.5/M 混合价，需替换真实单价） | GitHub 请求/日 |
|---|---|---|---|---|
| 1,000 | ≈1 | 29M | ≈$14.5 | ≈9k |
| 5,000 | ≈4 | 145M | ≈$72 | ≈45k |
| 10,000 | ≈7 | 290M | ≈$145 | ≈90k |
| 50,000 | ≈35 | 1.45B | ≈$725 | ≈450k |

> 90k 请求/日 ≈ 3,750/小时，单 PAT 的 5,000/小时**峰值很容易打满**。
> 上量前必须：① 结果缓存降低重复请求；② 多 Token / GitHub App；③ 评论与 README 长 TTL。

## 阶段 7｜多个用户提相同问题：怎么复用结果

这是"省成本"和"降延迟"性价比最高的一环。分四层，逐层加复杂度：

### 7.1 第一层：精确结果缓存 ✅

- **Key**：`sha256(tenant, repo, issue, 用户补充哈希, 模型名, Prompt 指纹)`。
- **为什么带 Prompt 指纹**：改了 Prompt 还返回旧结论，是最难排查的"幽灵 bug"。
  `prompts.py` 里对全部 Prompt 取哈希，任何改动自动失效。
- **为什么带租户**：避免跨租户泄露（即使内容都是公开数据，审计上也不该混）。
- **TTL**：默认 900s。Issue 被编辑/新评论 → 最长 15 分钟后才更新；
  对"正在排查中"的场景可把 TTL 调到 60s，或把 `issue.updated_at` 纳入 key。
- **只缓存成功结果**：`partial`/`failed` 不缓存，避免把一次预算耗尽固化成 15 分钟的"标准答案"。
- **命中提示**：返回 `cache: {hit, age_seconds, hits}`，前端显示"这是 3 分钟前的结果"。

代码：`results.py::ResultStore`、`runner.run`。
验证：`test_second_identical_run_hits_cache`、`test_partial_results_are_not_cached`。

### 7.2 第二层：并发合并（防缓存击穿）✅

缓存写入前的那几秒，10 个相同请求会同时穿透。用 Single-flight 让第一个执行、其余等待共享结果。

- 只对**同步、无事件流**的调用生效（流式请求各自需要自己的 span 流）；
- 等待者拿到同一份结果并标记 `cache.shared=true`；
- 异常也会原样传给等待者，避免"第一个失败、其余重跑"。

代码：`results.py::SingleFlight`、`runner.run`。
验证：`test_concurrent_calls_execute_once`。

### 7.3 第三层：作业去重 ✅

异步作业按同一 key 去重：运行中的作业直接复用，前端连同一个事件流。
代码：`JobManager.submit(..., dedupe_key=...)`，key 与结果缓存同源。

### 7.4 第四层：语义近似复用 🟡（生产建议）

很多人问的是"同一个问题的不同表述"（`升级后超时` vs `2.4 版本 search timeout`）。

设计：
1. 对 `repo + 规范化问题文本（标题 + 错误码）` 生成 embedding；
2. 同仓库内余弦 ≥ 0.95 且关键实体（版本号/错误码）一致 → 复用；
3. 返回时标注"近似问题，来源 #123"，并缩短 TTL；
4. 版本/环境不同则**禁止**复用（这是最容易翻车的地方）。

代价：一次 embedding 调用 + 一个向量索引；收益：长尾重复问题命中率显著提升。
本项目未实现（离线向量是哈希的，不适合做语义判重），但接口位置已留好：
把 `ResultStore` 换成"精确 + 向量"两级即可。

### 7.5 失效与一致性

| 触发 | 处理 |
|---|---|
| Issue 被编辑/新评论 | TTL 到期；或把 `updated_at` 纳入 key（多一次 GitHub 请求，省一次 LLM） |
| Prompt / 模型变更 | 指纹变化，自动全量失效 |
| 结论被用户点踩 | 主动删除该 key（反馈闭环） |
| 降级结果 | 不缓存 |
| 结果里含"证据不足" | 可缓存但 TTL 缩短（如 300s） |

**观测**：`analysis_cache_hits_total`、`analysis_cache_misses_total`、
`analysis_singleflight_shared_total`、`/api/v1/stats.results.reuse_ratio`。
命中率低 → 检查 key 是否带了易变字段（如时间戳、随机 request_id）。

## 阶段 8｜搜索后 RAG 召回失败：从"没结果"到"可解释的没结果"

### 8.1 处理原则

1. **先区分"没搜到"和"没搜"**：`queries` 为空、工具失败、轮次耗尽，是三种不同的问题。
2. **能自动兜底的就兜底**：错误码回退检索、换词重试、换工具（KB → GitHub）。
3. **兜底不了就诚实**：写 `gaps`、输出降级报告，绝不编一个"可能原因"。
4. **每次失败都要可观测**：哪些查询词空了、是否回退、最终证据数。

### 8.2 已实现的兜底链

```
search_issues(query=模型给的词)
  ├─ 命中 → 加入证据
  └─ 为空
       ├─ build_fallback_query(错误码/异常名/状态码) → 再搜一次   ← 不花 LLM 调用
       │    ├─ 命中 → 用回退结果，warning 里写清"原检索为空"
       │    └─ 仍空 → retrieval_empty_total + "该仓库可能确无同类问题"
       └─ 工具异常 → 观测 + warning，继续下一步
```

为什么用错误码：GitHub 搜索对整句自然语言很差，对 `ReadTimeout`、`SEARCH_TIMEOUT`、
`401` 这类 token 命中率高。这是一个**零模型成本、可解释**的兜底。

### 8.3 召回失败的产品化处理

| 情况 | 报告里怎么写 | 用户下一步 |
|---|---|---|
| 仓库确无同类问题 | "未找到相关历史 Issue" + 已尝试的检索词 | 提供完整错误栈/版本 |
| 有相关但证据不足 | 低置信度假设 + `gaps` | 按建议补日志 |
| 数据源失败 | 明确是 GitHub 错误 + `code` | 重试/配 Token |
| 预算耗尽 | 降级报告 + 已抓证据摘录 | 调预算或 resume |

### 8.4 度量召回质量

| 指标 | 位置 | 用途 |
|---|---|---|
| Recall@5 / MRR | 离线评测 | 检索改动的回归门禁 |
| `retrieval_fallback_total` | `/metrics` | 兜底触发频率（高说明主查询太差） |
| `retrieval_empty_total` | `/metrics` | 真·无结果比例 |
| 证据数分布 | `metrics.evidence_count` | 长期偏低说明召回有问题 |
| "点踩 + 报告说证据不足" | 反馈表 | 最值得人工看的样本 |
| 引用覆盖率 | 评测 | 结论有多少条有依据 |

## 阶段 9｜运营迭代：让它越用越准

| 问题 | 症状 | 解法 | 状态 |
|---|---|---|---|
